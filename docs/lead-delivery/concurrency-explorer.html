Lead Lab · delivery concurrency

Many things at once, one lead, never lost or sent twice by mistake

Intake, operators, the firm portal and the delivery worker all touch the same leads at the same time, and the worker has up to 20 requests on the wire. Four rules keep that safe. Step through each race below to see which transaction decides it. The reference is docs/lead-delivery/concurrency.md.

The model

Four rules

One write at a timeEvery change is one short transaction through Db.write, behind one lock. A check and its write cannot be overtaken.
Never call out inside a transactionRequests to receivers and CRM lookups happen between transactions, never during one.
A lease with a versionA worker claims a delivery (owner, 5-minute expiry, version +1). Every later write checks the version still holds.
Record the start before sendingThe attempt is written as started first, so a lost answer is known to be unknown, never assumed unsent.
