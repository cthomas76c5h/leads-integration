How the lab works, from a lead's point of view

A lead comes in, gets one planned delivery per destination, and a worker sends each one until it ends in a recorded state. Everything else configures that, reads it back, or bills for it. Follow the example lead below, or pick any table or flow.

lead in→ plan: one delivery per destination→ attempts, retries, fallback→ outcome + hand-off, read back

    Learn it in this order

    • docs/lead-delivery/code-map.md: each flow in the order it runs, with files and functions, kept current with the code.
    • backend/tests/Tests/*.fs: each test names a behaviour; HandOffTests.fs and CoreTests.fs are the rules in miniature.
    • python tools/run_scenarios.py dead-endpoint: one story end to end against a fresh lab; its file in docs/contracts/scenarios/ says what should happen at each step.
    • The lab itself (cd backend && dotnet run --project src/Api, port 5080): open a lead, then its deliveries and attempts; the Delivery Center drawer shows the exact request and answer.
